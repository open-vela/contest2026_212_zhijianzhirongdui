# 多模态身份确认技术调研与方案设计

> 项目: 研电赛 Seeed+小米赛道 — 分布式身份感知节点  
> 日期: 2026-06-07 | 版本: v1.0

---

## 一、问题定义

在智能空间场景中，摄像头从不同角度捕捉行人。核心任务是：**在不依赖人脸（侧身/背面/远距离/低光照）的条件下，仅通过体态和行走方式识别"这个人是谁"。**

### 子问题

1. **步态识别** — 从行走序列提取个体特征
2. **行人重识别 (ReID)** — 跨摄像头匹配同一人
3. **步态录入问题** — 管理员只有人脸照片，如何自动采集体态数据
4. **隐私保护** — 原始图像不出设备

```
                      "这个人是谁？"

          ┌────────────────┼────────────────┐
          ▼                ▼                 ▼
      人脸识别          步态识别            ReID
    (Face Rec)       (Gait Rec)       (Person Re-ID)
          │                │                 │
   输入: 面部RGB      输入: 行走序列      输入: 全身RGB
   强项: ★★★★★       强项: 不受光照/     强项: 多摄像头
         近距离+正面    衣着/距离影响            跨视角
   弱项: 需正面近距    弱项: 需行走+       弱项: 衣着变化
                        2D轮廓依赖              外观依赖

三者本质相同——都是"从视觉信号中确认人的身份"。
区别在于用哪种信息、在什么条件下可用。
前沿方向是三者的动态融合。
```

## 三、关键论文调研

### 3.1 主流步态识别模型

| 模型 | 出处 | 引用 | 参数量 | 输入 | 特点 |
|------|:----:|:----:|:------:|------|------|
| **GaitSet** | AAAI 2019 | 700+ | ~2.5M | 轮廓序列 | Set-based，任意帧数，跨视角 |
| **GaitPart** | CVPR 2020 | 400+ | ~1.5M | 轮廓序列 | 人体部位分割，更轻量 |
| **GaitGL** | ICCV 2021 | 300+ | ~3.0M | 轮廓序列 | 全局+局部特征融合 |
| **OpenGait** | arXiv 2023 | 150+ | 可配 | 统一框架 | 支持 silhouette/skeleton/pose |

> 上述模型均为**身份识别**（区分不同人），不是动作分类（区分走路/跑步）。训练数据集为 CASIA-B/OU-MVLP（按人分组，不是按动作分组）。

### 3.2 前沿方向：无约束 + 轻量化

| 论文 | 年份 | 核心贡献 | 参数量 | 能否上 ESP32-S3 |
|------|:----:|------|:------:|:---:|
| **GaitKD** | 2024 | 知识蒸馏，MobileNetV2 学生模型 | ~1.0M (INT8 ~500KB) | ✅ |
| **Distillation-guided Unconstrained Gait** | 2024 | 无约束场景（室外/任意角度）的蒸馏训练 | ~1.5M (INT8 ~750KB) | ✅ |
| **TrackletGait** | 2025 | 任意长度片段（不要求完整步态周期），时序注意力 | ~2.5M (INT8 ~1.2MB) | ⚠️ 勉强 |
| **Dense 3D Gait Representations** | 2024 | 3D 人体重建替代 2D 轮廓，天然对抗视角变化 | HMR ~50M + Gait ~2M | ❌ HMR 太重 |

| 论文 | 年份 | 核心贡献 |

### 5.2 ESP32 端零模型、零推理

```
ESP32-S3 内存占用分析:
  - 摄像头 DMA 帧缓冲: 32KB (已有)
  - 背景模型 (running avg): 160×120×8bit / 4 ≈ 5KB
  - 二值轮廓缓冲: 64×44 bits ≈ 352 bytes
  - MQTT 发送缓冲: 2KB
  ─────────────────────────────
  总计新增: ~8KB (完全可以忽略)

  已占用 (系统+MobileFaceNet): ~2.5MB
  剩余 PSRAM: ~5.5MB
```

**ESP32 上不需要任何额外模型**——帧差法是纯 C 语言的像素加减法，等同于：

```c
for (int i = 0; i < width * height; i++)
    silhouette[i] = abs(frame[i] - background[i]) > threshold ? 1 : 0;
```

### 5.4 Corridor 场景可行性分析（关键）

**你的场景**: 摄像头固定在走廊墙壁，人从一侧走向另一侧。

```
摄像头 (固定)
  │
  ├─ 远: 小人影 (正面/背面)    ~5m, 视角≈0°/180°, 轮廓≈10px
  ├─ 中: 中等大小 (斜侧)       ~3m, 视角≈45°/135°, 轮廓≈25px
  └─ 近: 大人影 (侧向)         ~1m, 视角≈90°, 轮廓≈50px

  人 →→→→→→→→→→→→→ 走过
```

**经典步态论文 (GaitSet/GaitPart/GaitGL) 能否直接用？**

❌ **不能直接适用**。原因：
- 它们训练在 CASIA-B/OU-MVLP 上：人在跑步机固定位置走，多摄像头各拍固定角度
- 论文的 "cross-view" 指"注册=90°序列，测试=54°序列"，**两个都是固定距离+固定角度**
- 你的场景中：距离变化 5×、视角连续变化 180°、轮廓大小不恒定

**验证数据 (GaitSet CASIA-B Rank-1)**：
| 注册\探测 | 0°(正面) | 54° | 90°(侧面) | 180°(背面) |
|-----------|:------:|:---:|:--------:|:---------:|
| 0° | — | 75% | 68% | 80% |
| 90° | 72% | 87% | — | 70% |

**三种解决方案 (针对 corridor 场景)**：

| 方案 | 原理 | 可行性 | 精度预期 |
|------|------|:---:|:------:|
| **A: 滑窗归一化** | corridor→正面/侧面/背面三片段→各自归一化→分别推理→投票 | ⭐⭐⭐ | ~70% |
| **B: TrackletGait** | 2025论文, 无约束, 不要求完整周期+固定视角 | ⭐⭐⭐⭐ | ~80% |
| **C: 3D重建** (方案C+D) | 轮廓→3D网格→旋转到标准侧面→提取embedding | ⭐⭐⭐⭐⭐ | ~85%+ |

**方案 C 恰好完美解决 corridor 的两个致命问题**：
1. 距离变化→轮廓大小不一 → 3D 重建后人体是真实尺度 → 归一化即统一
2. 视角连续变化 → 3D 网格可旋转到标准侧面 → 等同于论文的"90°固定视角"

这也是为什么**方案 C+D（轮廓上传+服务器 3D 重建）是最佳路径**——它不仅保护隐私，而且架构上天然兼容 corridor 场景。如果坚持端侧 GEI+CNN（方案 A），corridor 下的距离/视角变化会严重降低精度。

## 六、步态自动录入机制

```
员工入职:
  1. HR 录入人脸照片 → 创建 user 记录
  2. user.gait_status = "pending"

走廊无感采集:
  3. 员工经过走廊 → Face 高置信度识别 (>0.9)
  4. 同步采集步态轮廓 → 服务器提取 gait_emb
  5. UPDATE user SET gait_emb = EMA(新值, 旧值)
  6. 累计 N≥10, gait_emb 方差 < 阈值 → gait_status = "active"

此后:
  7. 人脸不可用时 → 仅用 gait_emb 识别
  8. Faiss 多模态融合: w_face×cos(face) + w_gait×cos(gait)
```

| 问题 | 答案 |
|------|------|
| 管理员需手动录步态吗？ | 不需要。人脸识别时自动"搭便车" |
| 新员工多久激活步态？ | ~2-3 天（走廊经过约 10 次） |
| 数据如何关联？ | 时间窗口 ±3s 自动配对 |
| 论文支撑？ | Database-Agnostic Gait Enrollment (arXiv 2025) |

## 八、FAQ：关键质疑与解答

### Q1: 二值轮廓 → 骨骼关节点，真的可行吗？

**A: 可行。单帧轮廓有歧义，但连续序列的时序约束消除了歧义。**

单帧轮廓确实可能对应多种姿势（侧身站立 vs 手臂前伸）。但连续 30 帧的轮廓序列中，"两腿交替的变化模式""手臂摆动的相位"等时序信息唯一确定了 3D 姿态。

学术支撑（20 年积累）：
- Agarwal & Triggs (ECCV 2004, 2000+ 引用): 首次证明从单目轮廓序列恢复 3D 姿态
- Sigal et al. (IJCV 2010, 800+ 引用): HumanEva 标准基准，输入=轮廓序列，输出=3D 关节
- Mehta et al. (3DV 2017, 1500+ 引用): VNect，时序 CNN + 轮廓 → 精确 3D 关节
- CASIA-B 数据集（步态识别标准基准）：恰好就是轮廓序列

从轮廓提取关节点比从 RGB 图像更简单——输入已经是"纯人体形状"，问题退化为几何问题（找白色块的凸起=四肢端点），不需要理解颜色/纹理/衣着。

### Q2: 帧差法/自适应阈值等预处理的算力？

**A: 极轻。帧差法 ~10ms, Otsu 自适应 ~25ms。合计约 MobileFaceNet 的 1/3。**

| 操作 | 运算量 | ESP32-S3 延迟 |
|------|:------:|:------------:|
| 帧差法 (19200 像素) | 19200 次减法+绝对值 | ~8ms |
| Otsu 自适应阈值 | 256-bin 直方图+遍历 | ~15ms |
| 二值化 | 19200 次比较 | ~3ms |
| 人体检测 (连通域) | 一次 BFS | ~5ms |
| **合计** | — | **~30ms/frame** |
| MobileFaceNet (参考) | ~300M MACs | ~85ms |

Otsu 自适应阈值**推荐使用**——走廊光线不均匀时（一端有窗一端暗），全局固定阈值可能在暗处把人"切没了"。Otsu 自动为每帧计算最优阈值。

### Q3: 方案 C 和方案 D 是否会导致 ESP32 不堪重负？

**A: 不会。方案 C 不需要模型（纯 CV），方案 D 移到了服务器上执行。**

ESP32 只做方案 C（帧差法→轮廓→MQTT 上传）。服务器从轮廓中提取关节点（方案 D）。ESP32 新增内存 ~8KB，无任何新模型。
