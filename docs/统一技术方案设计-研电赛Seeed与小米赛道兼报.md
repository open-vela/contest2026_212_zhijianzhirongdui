## 三、多模态无感身份确认架构

### 3.1 设计原则

**"分层融合、逐级确认、动态权重"**——不依赖单一模态，而是根据不同场景下的模态可用性、置信度、隐私等级，动态调整融合权重。

### 3.2 四层身份确认体系

```
                      有感 ←──────────────────────→ 无感
                      （主动配合）                  （被动感知）

Layer 0: 显式认证    ── 仅用于最高安全场景（如进入服务器机房）
Layer 1: 近场隐式    ── 手机BLE/WiFi指纹，不需要掏出设备
Layer 2: 生物特征    ── 人脸识别，不需要携带设备但需正对摄像头
Layer 3: 行为特征    ── 步态/体态，完全无感，远距离可用
Layer 4: 时空模式    ── 习惯/轨迹预测，辅助降低误识率
```

### 3.3 各模态技术实现

#### 人脸识别

| 参数 | 取值 |
|------|------|
| 模型 | MobileFaceNet (INT8量化) |
| 嵌入维度 | 128-d |
| 推理延迟 (ESP32-S3) | ~85ms |
| 内存占用 | ~0.8MB |
| 部署位置 | 从节点（入口、走廊关键位置） |
| 适用条件 | 光照充足、正面或小角度偏转 |

#### 步态识别（无感辅助核心）

**学术支撑**：
- FarSight (IARPA BRIAR, 2025)：人脸+步态+体型三模态融合，TAR@0.1%FAR 下精度提升 34.1%
- GitHub 开源实时系统 (2025)：YOLOv8+InsightFace+OpenGait，95%+ 准确率，~200ms 延迟
- GBIFS 步态-虹膜融合：99.997% 准确率

**本方案实现**：

```
走廊侧向摄像头 (OV2640, 视角覆盖行走路径)
    │
    ▼
从节点 ESP32-S3 运行:
  ┌─────────────────────────────┐
  │ 轻量 Gait Pipeline          │
  │ 1. 背景减除 → 人体轮廓提取   │
  │ 2. GEI (步态能量图) 生成     │
  │    - 一个步态周期 ~1.2s      │
  │    - GEI = 平均N帧轮廓       │
  │ 3. 轻量 CNN → 64-d Gait Emb │
  │ 4. 延迟: ~80ms/frame        │
  └─────────────────────────────┘
```

| 参数 | 取值 |
|------|------|
| 输入 | 连续人体轮廓帧 (~30帧/步态周期) |
| 模型 | 轻量 2D-CNN (3层 Conv + FC) |
| 嵌入维度 | 64-d |
| 推理延迟 | ~80ms per GEI |
| 适用条件 | 侧向摄像头、正常行走速度、任意光照 |

#### BLE 手机指纹（隐式概率增强）

**工业参考**：NHI Continuous Recognition Platform (33bit, 2025)，将 WiFi/BLE/蓝牙经典/GPS 信号关联为 "NHI-Persona"

**本方案实现**：
- 走廊中的 ESP32-S3 从节点周期扫描 BLE Advertising
- 利用 BLE Privacy 1.2 的 MAC 轮转机制，通过 IRK (Identity Resolving Key) 解析真实身份
- RSSI 信号强度随距离衰减的曲线作为"人在附近"的概率增强信号
- **不作为独立身份确认手段**，仅用于提升其他模态的置信度

#### 动态权重融合

```
Fused_ID_Score =
    w_face(t)   × Face_Similarity(当前嵌入, 注册嵌入)
  + w_gait(t)   × Gait_Similarity(当前GEI嵌入, 注册嵌入)
  + w_ble(t)    × BLE_Proximity_Score(当前RSSI, 预期RSSI)
  + w_traj(t)   × Trajectory_Consistency(当前轨迹, 历史模式)

w_i(t) = f(模态质量, 环境条件, 遮挡程度, 用户速度)
```

**权重动态调整规则**：

| 场景 | w_face | w_gait | w_ble | 说明 |
|------|:------:|:------:|:-----:|------|
| 正面走向摄像头 | 0.7 | 0.2 | 0.1 | 人脸最佳状态 |
| 侧身经过走廊 | 0.1 | 0.6 | 0.3 | 步态为主，人脸不可用 |
| 背对摄像头远离 | 0.0 | 0.5 | 0.5 | 人脸完全不可用 |
| 多人拥挤 | 0.2 | 0.1 | 0.7 | 视觉模态均受限，BLE相对可靠 |
| 低光照 | 0.1 | 0.6 | 0.3 | 人脸失效，步态对光照不敏感 |

### 3.4 隐私保护的分区分级策略

| 区域类型 | 身份识别级别 | 数据留存 | 说明 |
|----------|:----------:|----------|------|
| 公共区域（走廊、电梯间、大堂） | **全模态融合** | 匿名嵌入+时间戳 30天 | 正常无感身份确认 |
| 会议室（使用中） | **全模态 + 行为记录** | 会议结束后 7 天自动清除 | 支撑会议智能功能 |
| 工位区 | **部门级粗粒度** | 仅占位统计 | "有人/无人"，不做个人身份 |
| 敏感区域（厕所、母婴室、医疗室） | **仅 PIR 占位感知** | 即时丢弃 | 绝不做任何身份识别 |
| 服务器机房/财务档案室 | **Layer 0 显式认证** | 完整审计日志 90 天 | 最高安全级别 |

**隐私保护技术措施**：
- **原始图像不出设备**：OV2640 采集 → 推理 → 仅输出特征向量和检测框 → 原始帧立即丢弃（Bultmann, Univ. Bonn PhD 2024 论证的语义级协同原则）
- **身份嵌入不可逆**：Face/Gait Embedding 经单向哈希后存储，参照 FaceCloak (IEEE FG 2025) 的可再生二值掩码方案
- **BLE MAC 轮转**：使用 LE Privacy 1.2，MAC 地址每 15 分钟轮转
- **透明告知 + 员工可控**：入口隐私告知标识；员工可通过 App 查看自己被记录的事件日志，可选择删除或暂停特定区域的识别

## 四、MiMo-VL 模型结合分析

### 4.1 MiMo-VL-Miloco-7B 技术概要

| 项目 | 详情 |
|------|------|
| 论文 | Xiaomi MiMo-VL-Miloco Technical Report, arXiv:2512.17436, Dec 2025 |
| 代码/模型 | github.com/XiaoMi/xiaomi-mimo-vl-miloco (开源, Apache 2.0) |
| 模型架构 | ViT + MLP Projector + 7B LLM |
| 训练方式 | 两阶段：SFT (CoT监督+Token-Budget感知) → GRPO强化学习 |
| 家庭场景 F1 | 手势识别 86-99%，活动识别 90-99% |
| 通用基准 | MMMU-Pro 55.7%, Video-MME 68.0%, MATH500 95.2% |
| 量化版本 | GGUF 4bit → 内存 ~4GB (FP16 的 ~14GB 降至 4GB)，精度损失 ≤1 F1 |
| 已知局限 | 家庭活动类别仅5种+5种手势；缺少跨布局泛化评估；无音频/毫米波模态 |

### 4.2 能否用于本项目？

**可以用于演示的场景级理解，但不可在 RDK X3 上运行。** 经核查 GitHub 仓库 (XiaoMi/xiaomi-mimo-vl-miloco) 和 HuggingFace 发布的 GGUF 模型：

| 组件 | 大小 |
|------|------|
| GGUF Q4_0 量化后的语言模型 | ~4.2 GB |
| Vision Projector (CLIP ViT) | ~1.3 GB |
| **合计** | **~5.5 GB** |

**修正声明**：之前认为 4GB 即可运行的判断是错误的。GGUF Q4_0 量化的是 7B 语言模型部分，但 **Vision Projector 不可省略**，运行时至少需要 **~6GB RAM**。RDK X3 仅 4GB，**无法运行**。

**替代方案**：
1. **在开发 PC / 服务器上运行**（推荐）：直接 python -m llama_cpp 加载 GGUF，按需调用
2. **Orange Pi 5 Plus**（8GB, 6TOPS, ¥500）：可部署 GGUF 模型
3. **演示时按需调用**：不是每帧都推理，只在"会议室多人活动"等特定场景触发，降低延迟压力

### 4.3 能否自主微调？

**可以。** MiMo-VL-Miloco 的完整训练流程已公开：

- **SFT 阶段**：使用 AdamW (batch size 128, lr=1×10⁻⁵, 序列长度 32,768)，可替换训练数据为自建的"智能办公场景"数据集
- **GRPO 强化学习阶段**：使用 Group Relative Policy Optimization，多部分奖励设计（准确度 0.9 + 格式合规 0.1），可定义办公场景专用奖励函数
- **LoRA 高效微调**：7B 参数模型的全量微调需要多卡 GPU (>40GB 显存)，但使用 LoRA (rank=64) 可在单张 24GB GPU 上完成微调，训练时间 ~12-24 小时

### 4.4 建议的微调方向

| 微调目标 | 所需数据 | 预期效果 |
|----------|----------|----------|
| **办公场景活动识别** | 标注视频：走路/站立/坐下/开会/打电话/使用电脑/走向电梯/进入房间 | 从 5 种家庭活动扩展到 15-20 种办公活动 |
| **时空意图分类** | 标注序列：{位置轨迹 + 时间 + 日历事件} → {目的地标签} | 使模型能直接从视频序列推断"这个人要去哪儿" |
| **设备控制指令生成** | {场景描述 + 用户偏好} → {设备控制 JSON} | 使模型能将自然语言场景理解转换为 MCP 设备控制指令 |
| **异常行为检测** | 标注异常事件：尾随进入/非工作时间进入敏感区/徘徊/奔跑 | 使模型能识别安全相关异常行为 |

### 4.5 本方案中的分层部署策略

```
Layer 0 (ESP32-S3 从节点):  轻量视觉模型 (MobileNetV3/MobileFaceNet/Gait-CNN)
                             → 实时、低延迟 (<150ms)、低功耗
                             → 输出：检测框 + 身份嵌入 + 事件标签

Layer 1 (ESP32-S3 主节点):  多模态融合 + LLMAC-Lite 访问控制
                             → 延迟 <10ms、规则+决策树
                             → 输出：身份确认 + 访问决策 + 自然语言解释

Layer 2 (RDK X3 / PC):      MiMo-VL-Miloco GGUF (可选认知层)
                             → 延迟 ~500ms-2s、高算力
                             → 输出：复杂场景语义理解 + 时空意图推断
                             → 非必需：基础演示中 Layer 0+1 即可闭环
```

**关键设计**：MiMo-VL 在方案中定位为**可选的认知增强层**——论文中完整描述其微调方案和部署架构，代码仓库提供微调脚本和推理接口，但基础演示不依赖它。这既展示了技术深度，又不增加演示失败风险。

### 4.6 不依赖 MiMo-VL 的轻量替代方案（兜底）

如果 RDK X3 无法及时到位或微调时间不足，时空意图推断可以用**规则引擎 + 轻量 LSTM** 在 ESP32-S3 上实现：

```
输入: 过去 60 秒的轨迹坐标序列 (10 个采样点，每 6 秒一个)
     + 当前时间 (小时)
     + 日历事件 (下一个会议的时间+楼层，通过 API 获取)

LSTM (2层, hidden=64) → 3 层 MLP → Softmax over {工位, 会议室, 咖啡角, 电梯, 出口}

模型大小: ~200KB (INT8量化)
推理延迟: ~15ms on ESP32-S3
训练: PC端离线训练，部署时权重冻结
```

## 六、CLCP 协议与发现-连接-协同-反馈闭环

### 6.1 设备发现（目标 ≤1s）

**双模并行**：BLE Advertising (100ms 间隔，携带设备类型+能力描述符) + mDNS 服务注册 (`apps/netutils/discover/`)。两通道竞速，取先到者。

### 6.2 连接建立（目标 <100ms）

**ESP-NOW 无连接直连**：MAC 层对等通信，无 WiFi 关联/DHCP 流程。控制面通过 BLE GATT 配置。

### 6.3 断连重连（目标 <2s）

心跳帧 500ms 间隔 × 连续 3 帧未收到 = 断连判定 → BLE 重扫描 + ESP-NOW peer 重注册。

### 6.4 数据传输性能

- ESP-NOW 端到端延迟 <10ms（满分标准 ≤50ms）
- 应用层序列号 + 选择性重传，1h 压测 360,000 帧丢包率 <0.1%

### 6.5 "发现→连接→协同→反馈"全闭环

```
  发现          连接          协同            反馈
BLE+mDNS  →  ESP-NOW绑定  →  多节点感知  →  uORB消息发布
<1s          <100ms          身份融合       OLED显示
                              访问控制       手机通知
                              设备控制       超声波定向音响
                              任务流转       管理端Dashboard
```

## 十四、创新点总结

1. **四层多模态无感身份确认体系**（Face + Gait + BLE + Trajectory）：首次在拇指级硬件上实现动态权重的多模态身份融合，人脸对光照敏感时自动升权步态，低光照下步态不受影响。

2. **openvela 在 XIAO ESP32S3 Sense 的首次完整移植**：21×17.5×15mm 极端体积约束下的全功能分布式 AIoT 操作系统运行。

3. **LLMAC-Lite 可解释访问控制引擎**：将 LLMAC 框架 (Zisad & Hasan, 2026) 的 LLM 驱动访问控制理念适配为规则引擎+决策树混合架构，每个决策附带自然语言解释。

4. **CLCP 原创协同协议**：专为 MCU 级分布式协同感知设计的二进制帧协议，集成设备能力描述符、服务注册表、任务迁移状态机和置信度门控字段。

5. **时空意图推断 (LSTM 轻量版 + VLM 认知版)**：两层意图推断——轻量 LSTM (15ms, 200KB) 做实时预测，Qwen3-VL-8B / MiMo-VL-7B-RL (按需) 做复杂语义推理。借鉴 AutoTraces (CVPR 2026) 的轨迹 Token 化范式。

6. **30 项智能建筑场景全覆盖**：从无感通行、电梯调度到心理健康监测，每个场景均有真实企业案例支撑（安克深圳/华为福田/腾讯滨海/Accenture/VergeSense）——详见 §15.8。

7. **三层分层架构 + 分区隐私保护**：感知层→融合层→认知层三层解耦；5 级区域隐私分级（公共→工位→敏感），原始图像不出设备。

8. **OTA 安全固件升级**：自研 A/B 双分区 + MQTT 触发 + HTTP 下载 + 原子切换 + 自动回滚，保证企业级设备持续迭代。

### 15.3 Corridor（走廊）场景分析

**场景特点**：
- 人在走廊固定路径上走过（非跑步机）
- 距离 1m（近距）→ 5m（远距），变化 5 倍
- 视角连续变化 0°~180°
- 背景固定（可做背景减除）

**步态识别在 Corridor 的挑战**：
- CASIA-B/OU-MVLP 等经典数据集：跑步机上行走，固定距离 + 固定视角
- → 论文模型（GaitSet/GaitPart/GaitGraph/GEI-CNN）**不能直接适用**

**Corridor 适用方案（C+D 混合）**：

```
摄像机捕捉 → 帧差法提取二值轮廓 (ESP32, ~30ms/frame)
           → MQTT 上传轮廓序列 (8KB × 15fps × 5s = ~600KB/次)
           → 服务器：HMR 3D 重建 → 行进路径 + 姿态时序 → gait embedding
```

**为什么在 Corridor 不做端侧 CNN？**
- 帧差法 0 模型，~30ms/frame
- 场景变化太大，模型泛化必然差
- 3D 重建恰好解决距离/视角变化问题（多视角融合）

### 15.4 步态录入机制

**在 Corridor 中自动关联**（无需管理员手动录入）：
- 假设走廊两端均有摄像头
- 人从 A 走向 B，A 摄像头做人脸识别确认身份
- B 摄像头同步采集轮廓序列
- **时空共现关联**：相同时间在相邻摄像头捕获到的 face ID + gait silhouette → 自动关联为同一人
- 参考：OpenShoe (U of Toronto)、NIST BRIAR 评测 "database-agnostic enrollment"

### 15.5 传感器额外语义提取

从同相机流中低成本提取非身份信息：

| 语义 | 方法 | 算力 | 隐私风险 |
|------|------|:----:|:--------:|
| 占位/人数 | PIR + 人头检测 (轻量 YOLO) | 低 | 无 |
| 移动方向 | 光流 + 轨迹跟踪 | 低 | 无 |
| 携带物 | 前景面积异常检测 | 极低 | 无 |
| 行为类型 | Miloco/VLM (按需) | 高(服务端) | 中 |
| 尾随检测 | 人数突变 + 时间差 | 极低 | 无 |
| 摔倒 | 姿态变化率 | 低 | 中(需轮廓) |

### 15.6 时空意图推断

服务端汇聚各节点语义后推断：

```

走廊节点：blob=382, 方向=东→西, 速度=1.2m/s
```

## 十六、OTA 固件升级方案（v3.3 新增）

> **调研结论**：openvela 公开仓库中**无任何 OTA 机制**（GitHub API 搜索 ota/dfu 均为 0 结果），NuttX 主线也无标准 OTA 框架。需完全自建。

### 16.1 推荐方案：自建 A/B 双分区 OTA

```
                    MQTT(ota/command)
MQTT Broker ──────────────────────────────→ ESP32-S3
                                            │
内部 HTTP Server ←──── HTTP GET (Range) ────┘
(固件托管)
```

**Flash 分区设计 (8MB)**：
```
bootloader(64KB) | app_a(2.8MB) | app_b(2.8MB) | ota_data(8KB) | nvs(64KB) | user(~2.2MB)
```

**OTA 工作流**：
1. MQTT `ota/command` 下发 JSON `{version, url, sha256, size}`
2. ESP32 HTTP GET + Range 断点续传下载固件到非活跃分区
3. SHA256 校验 → 写入 OTA Data 标记为 `PENDING_VERIFY`
4. 重启 → Bootloader 切换到新分区
5. 应用自检通过 → 标记 `VALID`；失败 N 次 → 自动回滚到旧分区

**MQTT 协议**：
- `ota/command` ← 触发升级
- `ota/progress` → 进度上报
- `ota/status`   → 结果上报
- `ota/version`  → 设备上线版本上报

### 16.2 复杂度与时间

| 模块 | 难度 | 时间 |
|------|:----:|:----:|
| Flash 分区管理 | ★★ | 2-3天 |
| Bootloader 改造 | ★★★★ | 5-8天 |
| OTA Data 原子更新 | ★★ | 2-3天 |
| MQTT + HTTP 集成 | ★★ | 2-3天 |
| SHA256 + 断点续传 | ★ | 2-3天 |
| Rollback 状态机 | ★★★ | 3-4天 |
| 集成测试 | ★★ | 2-3天 |
| **总计** | | **18-28天** |

### 16.3 风险缓解

| 风险 | 等级 | 应对 |
|------|:----:|------|
| Bootloader 变砖 | 致命 | Factory 恢复分区 + 硬件引脚触发 |

## 十八、视频模型适配策略（v3.3 新增）

### 18.1 当前问题

MiMo-VL-Miloco-7B 训练数据：**5 种家庭活动 + 5 种手势**（做饭、打扫等）。而我们需要的：会议室讨论、尾随检测、异常徘徊、工位占位、摔倒检测……

### 18.3 推荐策略：梯度方案

**首选 (🥇)**：**Qwen3-VL-8B + LoRA + GRPO**

## 十九、BLE 蓝牙无感识别（v3.4 新增）

> 作为人脸+步态的**第三模态**，BLE 被动扫描在弱光/遮挡时提供补充置信度。

### 19.1 方案

ESP32-S3 被动扫描周围 BLE 广播包，匹配预注册员工设备（手机/手表/工牌），无需 App、无需配对。

| 特性 | 说明 |
|------|------|
| 扫描模式 | 被动扫描（Passive Scan），零用户操作 |
| MAC 随机化 | IRK 方案（配对获取 Identity Resolving Key） |
| 距离估算 | RSSI → 对数距离路径损耗模型，分 5 级（贴身/近/中/远/未知） |
| 融合权重 | BLE 提供 0.05~0.95 置信度，与人脸(0.5)+步态(0.3)加权融合 |
| 开发框架 | ESP-IDF NimBLE（预留 NuttX bt_* 适配层） |

### 19.2 代码模块

已实现 `ble_employee_scanner.c/h`（8.2KB），支持：
- NimBLE 被动扫描 + GAP 事件回调
- EMA 指数平滑 RSSI（α=0.3）
- 30秒超时自动标记离开
- 50 人数据库容量
- NuttX 适配层预留

## 二十、身体属性识别模型（v3.4 新增）

> 当人脸被遮挡或光线不足时，通过衣着颜色/体型/配饰等软生物特征辅助识别。

### 20.1 三方案对比

| 方案 | 模型大小(INT8) | 目标属性 | ESP32-S3 | 推荐部署 |
|------|:------------:|---------|:---:|------|

| **MobileNetV2 α=0.25** | 248KB | 衣物颜色/体型/身体嵌入 | ✅ | ESP32-S3 |
| **OSNet x0.25** | 600KB-1MB | 行人重识别 512-d 嵌入 | ⚠️ | 近端边缘(RPi) |

### 20.3 推荐实现路线

**首选**：PP-LCNet_x0_25 骨干 + TensorFlow/Keras 训练多任务 CNN，直接导出 TFLite INT8。

| 步骤 | 工具 | 产物 |
|------|------|------|
| 1. 数据准备 | PA-100K 数据集，筛选5属性标注 | TFRecord |
| 2. 模型训练 | Keras (PP-LCNet_x0_25 + 5分类头) | .h5 (~1.2MB FP32) |
| 3. INT8量化 | TFLite Converter PTQ | .tflite (~250KB INT8) |
| 4. C数组 | xxd -i | model_data.c (~700KB源码) |

- ESP32-S3 部署**方案一**（多任务轻量CNN），输出性别/上衣色/下衣色/背包/帽

## 二十一、多模态融合引擎（v3.4 新增）

已实现 Python 版 `fusion_engine.py`（7.3KB），核心算法：

```
自适应加权融合:
  weight_face = 0.50 × light_level + 0.20 × (1 - light_level)  ← 暗光降权
  weight_gait = 0.30  (不受光照影响)
  weight_ble  = 0.20
  
  多通道加成: 2通道 +15%, 3通道 +30%
  超时衰减: 5秒无更新 → 半衰
  滑动窗口: 10帧平均
```

集成在 `face_server.py` 中，MQTT 收到 ESP32 数据后实时融合。
